## 2. 计划用途与边界

### 2.1 用途

本文档用于：

1. 固定 M1 → M2 → M3 的实施顺序；
2. 按依赖关系把冻结设计拆成边界清晰的 Goal；
3. 说明每个 Goal 的目标、范围、上游依赖、交付物和最低验收条件；
4. 明确尚未决定的技术事项最晚应在哪个 Goal 前决定；
5. 防止把设计完成、代码存在、编译通过和业务验收混为一谈；
6. 为后续基于 `docs/GOAL_TEMPLATE.md` 编写正式任务说明提供路线图。

### 2.2 概念边界

```text
冻结设计目标
≠
实施计划
≠
已完成实现
≠
已通过验收
```

本文档不是：

- 已实现功能清单；
- 数据库 DDL；
- 业务流程、状态机、权限矩阵或数据库设计的替代文件；
- 每个 Goal 的详细需求或文件授权清单；
- 合规证明、GSP 检查结论或计算机系统验证结论；
- 项目完成报告。

### 2.3 产品与范围边界

- 产品范围只允许 `NATIONAL_DEFAULT` 和 `GD_DEMO_PROFILE`；
- M1 实现全国药品批发核心闭环，M2 才实现广东增强与正式质量事件展示，M3 最后完成演示加固；
- 广东监管和追溯能力只允许通过 Profile → Rule Pack → Adapter 的 Mock 方式展示；
- 不连接真实监管、追溯、物流或经营系统；
- 不引入特殊管理药品、疫苗、完整冷链、完整 WMS/WCS/TMS、多仓、多租户、微服务或财务总账；
- 本计划不改变 51 张候选表的冻结逻辑模型，也不把旧 Drug 原型作为新模块范例。

## 4. 计划原则

1. `docs/DEMO_SCOPE.md` 是最高产品基线，普通实施 Goal 不得隐含改变冻结范围。
2. 严格执行 M1 → M2 → M3；M1 未通过，不开始 M2；M2 未通过，不开始 M3。
3. 不一次实现全部 51 张表，不一次完成整个 ERP，不一次重写全部后端。
4. 每个 Goal 只处理一个清晰业务域或一个紧密相关的技术闭环。
5. 每个 Goal 必须可以独立理解、审查、测试、提交和回滚。
6. 数据库 DDL、Java 模型、Service、接口、最小页面和测试按依赖分阶段形成可运行闭环。
7. 采购订单不增加库存；收货与验收分离；验收合格后才形成批号库存。
8. 库存数量变化必须有不可删除流水；质量结论与冻结限制必须分离。
9. 未完成供应商、品种和客户必要准入前，不进入采购或销售实现。
10. 后端权限、状态守卫和职责分离是验收条件，前端隐藏按钮不能代替后端阻断。
11. 广东本地码核验 SM-15 与 Mock 交换 SM-16 分开实施、分开验收。
12. 旧 Drug 模块只代表当前实现现状；不得据此修改冻结设计或复制其旧状态、逻辑删除和字段模型。
13. “完成”必须有实际代码、脚本、自动化测试、数据库或 HTTP 断言及适用的浏览器证据。
14. 编译通过不等于业务验收通过，文档存在也不等于 Goal 完成。
15. 未决定的技术事项必须先作为实施前决策点关闭，不在本计划中擅自选择方案。

## 9. Goal 状态定义

| 状态 | 定义 |
| --- | --- |
| 未开始 | 尚未形成获准的正式任务或尚未执行实现；没有可接受的实现证据。 |
| 准备中 | 正在完成模板、正式任务说明、依赖核对或实施前决策；尚未开始该 Goal 的实现写入。 |
| 进行中 | 已按获准范围开始实现，但尚未达到全部交付物和最低验收条件。 |
| 待验收 | 实现和自检完成，证据已提交，等待业务或项目验收。 |
| 已完成 | 全部书面范围、交付物和最低验收条件已通过，并有可复核证据。 |
| 阻塞 | 存在未解决的范围冲突、上游依赖、决策或外部条件，当前无法安全继续。 |
| 取消 | 经人工决定不再实施；必须记录原因及对后续 Goal 的影响，不能用“取消”掩盖失败。 |

状态使用规则：

- 文档存在不等于 Goal 完成；
- 代码编译通过不等于业务验收通过；
- Goal 只有达到其书面验收标准后才能标记为“已完成”；
- `DB-BASE-01`已依据实施提交和真实验证证据标记为“已完成”；其他没有实现和验收证据的数据库及业务Goal不得标记为“已完成”；
- 未通过的测试、数据库断言、HTTP 或浏览器场景必须保留真实结果；
- 上游 Goal 未完成时，下游 Goal 原则上保持“未开始”，不能用并行开发制造跨域半成品。

## 10. Goal 准入和完成规则

### 10.1 准入规则

每个 Goal 开始前必须：

1. 完整阅读适用 `AGENTS.md`、本计划、上游冻结文档和最新 `CURRENT_STATE.md`；
2. 运行并核对 Git 分支、工作区、HEAD 和近期历史；
3. 使用完成后的 `docs/GOAL_TEMPLATE.md` 编写并冻结该 Goal 的正式任务说明；
4. 明确允许修改、新增、删除的文件，数据库和配置授权，以及禁止范围；
5. 明确角色、状态、阻断规则、事务、审计和浏览器演示边界；
6. 确认全部上游 Goal 已完成；
7. 关闭该 Goal 对应的实施前决策点；
8. 重新核验相关旧技术债，不把 `TECH_DEBT.md` 旧快照直接当作当前事实；
9. 如发现冻结文档冲突或需要范围变更，停止实现并由人工决定；
10. 明确计划运行的编译、自动化测试、数据库、HTTP 和浏览器命令。

### 10.2 完成规则

一个实现 Goal 只有同时满足以下条件才能进入“已完成”：

1. 实际代码、迁移、配置、脚本和适用页面已经进入该 Goal 的 Git 差异；
2. 未修改或创建 Goal 范围外文件；
3. 数据库变更可从隔离空 Schema 执行并有约束、索引和不变量断言；
4. Java 后端至少完成适用的编译和测试；
5. 正常、参数错误、业务阻断、权限不足、非法状态和审计场景均有测试；
6. 涉及库存时具有余额、流水、幂等、并发和事务回滚证据；
7. 涉及接口时具有真实 HTTP 结果；
8. 涉及用户操作时具有可重复的浏览器演示步骤和结果；
9. 测试失败、Mock 失败和外部条件失败不得伪装为成功；
10. 书面最低验收条件逐项通过，并由验收人确认；
11. 输出修改文件、表/字段/枚举/约束、流程、权限、状态、测试、风险、未完成项和最终 Git 状态；
12. 评估是否需要另行授权更新 `CURRENT_STATE.md`、`TECH_DEBT.md` 或其他动态文档，不在当前 Goal 中顺便扩大文件范围。

## 12. 变更与维护规则

1. 本计划是当前执行路线图；后续 Goal 应依据本计划的顺序、依赖和准入规则实施。
2. Goal 状态只能依据当前仓库实现和验收证据更新，不能依据预计完成时间更新。
3. 调整 Goal 顺序前必须检查上游依赖、业务硬规则和 M1 → M2 → M3 门禁。
4. 拆分 Goal 可以缩小风险，但合并 Goal 不得形成跨多个业务域的大任务。
5. 新增业务范围、角色、状态、表或真实外部接口，必须先按范围变更规则获得批准并同步冻结文档。
6. 冻结设计与实现计划发生冲突时，停止相关 Goal；不得用计划反向覆盖冻结设计。
7. 实施前决策点关闭后，应把结论写入对应正式 Goal 或获准的设计修订，不只保留口头结论。
