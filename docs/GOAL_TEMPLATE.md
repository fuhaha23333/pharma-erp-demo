> **核心定位：** 本文档用于编写 `pharma-erp-demo` 的每一个独立 Codex Goal，帮助任务发起人明确本次只做什么、依据什么、允许改什么、禁止改什么、如何验证以及什么条件才算完成。

## 2. 模板用途与使用规则

### 2.1 文档定位

本模板是独立 Codex 任务说明的统一骨架，不是：

- 某一个具体 Goal 的正式任务说明；
- 实施计划或业务设计文档；
- 已完成验收报告；
- 通用软件开发教程；
- 对冻结设计的修改授权。

### 2.2 一次只做一个 Goal

一个任务只能对应一个正式 Goal，不得一次完成多个业务域，不得顺带修复范围外技术债或重构未授权模块。不得修改冻结文档迁就现有代码；范围外问题只记录并报告。需要范围外文件、数据库对象、依赖或配置时，停止并请求新的明确授权。

### 2.3 填写与启用规则

1. 先从 `docs/DEMO_PLAN.md` 选择一个已满足上游依赖的 Goal；
2. 逐项填写本模板，不能用“相关文件”“适当测试”“必要权限”“视情况处理”等模糊表述；
3. 所有主字段都必须保留；不适用时填写“**不适用，并说明原因：`<明确原因>`**”；
4. 技术方案尚未确定时登记为实施前决策点，并写明最晚决定时点，不能擅自写成既定事实；
5. 正式任务说明经人工确认后，才授权 Codex 按其中边界执行；
6. 模板内容不能扩大 `NATIONAL_DEFAULT`、`GD_DEMO_PROFILE` 或 M1 → M2 → M3 的冻结边界。

## 4. 权威依据

### 4.1 优先级

具体 Goal 应按以下顺序判断边界：

1. 用户当前明确批准的 Goal 和文件、数据库、配置授权；
2. `docs/DEMO_SCOPE.md` 的具体章节和验收项；
3. 已冻结的业务流程、状态机、权限矩阵和数据库设计；
4. `docs/DEMO_PLAN.md` 中该 Goal 的顺序、依赖和决策点；
5. `docs/CURRENT_STATE.md` 的当前事实；
6. 适用的全部 `AGENTS.md`；
7. 已重新核验的 `docs/TECH_DEBT.md` 条目；
8. 现有代码惯例。

出现冲突时不得自行选择或扩大任务，应停止相关实现并列出冲突，等待人工决定。

### 4.2 精确引用要求

“权威文档”必须逐项列出本 Goal 涉及的：

`DEMO_SCOPE.md` 章节或 AC 编号、`BUSINESS_FLOW.md` 的 BF 编号、`BUSINESS_STATE_MACHINE.md` 的 SM 编号和转换、`ROLE_PERMISSION_MATRIX.md` 的权限编号，以及 `DATABASE_DESIGN_DEMO.md` 的章节、表和 DB-AT 场景；同时列出 `CURRENT_STATE.md` 的具体当前事实、`DEMO_PLAN.md` 的 Goal/上游依赖/实施前决策点，以及 `AGENTS.md` 的适用规则。

禁止只写“参考项目文档”。`TECH_DEBT.md` 是旧快照，引用条目前必须用当前仓库重新核验，并记录“仍成立、已变化或已失效”。

## 5. 开始前事实检查

具体 Goal 至少执行并记录：

```bash
git branch --show-current
git status --short
git rev-parse --short HEAD
git log --oneline --decorate -n 8
find .. -name AGENTS.md -not -path '*/.git/*' -print
```

随后必须：

1. 完整阅读所有适用 `AGENTS.md`；
2. 按正式任务指定顺序完整阅读权威文档；
3. 核对预期分支、HEAD、工作区状态和上游 Goal 证据；
4. 列出准备修改、新增、删除的文件，以及数据库、依赖和配置授权；
5. 对开发 Goal 说明涉及角色、状态、阻断规则、审计和浏览器演示；
6. 说明主要风险、计划运行的验证以及完成条件。

分支、HEAD、工作区或上游依赖不符合正式任务预期时，停止修改并报告。开始检查只能读取事实，不能为了满足预期而清理、暂存、提交、切换分支或改写历史。

## 6. 允许修改范围

文件授权必须分成四类：

```text
允许修改
允许新增
允许删除
明确禁止
```

数据库对象和依赖配置另行授权，不得由文件授权自动推导。默认规则是：

> **没有列入允许范围的文件、数据库对象、依赖和配置不得修改。**

路径必须精确到文件；确需目录范围时，应列出目录、允许的文件类型和数量边界。移动或重命名必须按“删除 + 新增”分别授权并审查。Codex 如发现必须修改范围外对象，应停止并报告，不得自行扩大范围，也不得留下临时文件或生成物。

## 7. 禁止修改范围

具体 Goal 至少明确：

- 不得修改的冻结设计、动态事实、计划文件、相邻模块、表、配置、依赖和测试；
- 不得连接或修改真实经营数据库、真实监管平台或真实经营数据，不得顺带处理技术债或重构；
- 不得创建、切换或删除分支，不得 commit、push、合并或创建标签，除非具体 Goal 明确授权；
- 不得把 Mock 结果描述为真实平台结果，也不得把编译或单项测试通过描述为业务验收完成。

“明确不包含”说明本 Goal 不交付的相邻能力；“禁止事项”说明执行期间不能发生的动作，两者都必须填写。

## 8. 实现要求

- 要求应能映射到明确文件、对象、规则和验收场景；
- 每个 Goal 形成一个业务域或紧密技术闭环，失败时可以整体回滚；
- 设计、DDL、Java 模型、Service、接口、页面和测试按 Goal 授权分阶段实施；
- 发现冻结设计未决定的细节时登记决策点，不得凭空创建字段、API、表或业务规则；
- 实现不得绕过首营、收货验收分离、库存流水、质量状态、独立复核、权限或审计；
- 实现结果必须以实际代码、脚本和证据为准，不能把计划或占位文件当作完成；
- 任何停止条件触发后，保留现场并报告，不用未授权修改“修好”现场。

## 9. 数据库要求

数据库 Goal 必须明确：

- 允许创建或修改的 Schema、表、列、约束、索引和种子数据；
- 隔离 Schema 和账号，测试 Schema 创建/清理权限，以及现有开发数据和真实经营数据边界；
- 数据库版本、InnoDB、字符集、排序规则、SQL Mode、会话时区、DDL 顺序、失败停止、重复执行和已执行脚本不可改写策略；
- 主键、外键、唯一约束、CHECK、必要索引、种子来源/数量/重复策略和敏感数据边界；
- 事务、锁顺序、并发、幂等、死锁、回滚，以及仓库内可重复运行且不篡改业务结果的验证脚本。

是否引入 Flyway、SQL 命名方式、重置策略、种子生成方式和测试数据库隔离方式，未由冻结文档或正式 Goal 决定时，只能登记为实施前决策点；非数据库 Goal 的相关字段仍须填写“不适用，并说明原因”。

## 10. Java后端要求

Java Goal 必须明确允许修改的模块和包，以及 Controller、DTO、Entity、Enum、Mapper、Service、VO 的范围；同时说明是否允许修改 POM、配置和依赖。

必须遵守：

- Controller 负责请求、校验、调用 Service 和返回结果，不得直接操作 Mapper；
- 同一业务事务由一个公开 Service 方法形成清晰边界；
- Service 负责业务守卫、状态转换、事务、职责冲突和 Mapper 调用；
- 异常与响应方式必须可测试，事务失败不能留下部分业务结果；
- 权限拒绝、非法状态和关键失败按 Goal 要求写审计；
- 单元、Spring、数据库集成、HTTP 测试按实际层级分别取证。

非 Java Goal 不能删除这些字段，应填写“不适用，并说明原因”。

## 11. 前端要求

前端 Goal 必须明确：

- 页面、路由、组件、状态管理和已冻结或经批准的 API 契约；
- 角色可见性、按钮状态、数据范围，以及参数、业务阻断、权限拒绝和系统错误展示；
- 验收账号、浏览器入口、逐步操作，以及构建、前后端联调和浏览器证据。

前端隐藏按钮不能代替后端权限阻断。非前端 Goal 仍须填写“不适用，并说明原因”。

## 12. 权限、状态和审计要求

具体 Goal 必须把“角色 + 权限编号 + 来源状态 + 动作 + 目标状态 + 守卫 + 审计”写成可验证规则：

- 列出允许角色、明确拒绝角色和同一实例的职责冲突；
- 状态转换只允许来自指定 SM 路径，失败后保持原状态；
- 申请、审核、批准、执行或独立复核不得被同一账号违规包办；
- 成功、失败、拒绝、修改原因、前后值和业务关联按权威文档记录；
- 状态历史、库存流水、审批、复核、Mock 尝试等不可变记录不得覆盖或删除；
- 日志和审计不得包含明文密码、密钥或不必要的敏感信息。

## 13. 测试与验收要求

### 13.1 证据必须分层

以下证据彼此不能替代：

```text
编译通过
单元测试通过
Spring 上下文测试通过
数据库约束验证通过
HTTP 验证通过
浏览器验证通过
业务 Goal 验收通过
```

### 13.2 每项测试结果

每项结果至少记录：

```text
命令
结果
测试数量
失败数量
错误数量
跳过数量
实际覆盖范围
不能证明的内容
```

没有计数概念的手工、HTTP、数据库或浏览器验证，应写“计数不适用，并说明原因”，并记录逐项断言结果。

### 13.3 场景与完成边界

按适用性覆盖正常、参数错误、业务阻断、权限拒绝、非法状态、并发与幂等、数据库约束和回滚场景。不适用的场景必须说明原因；不能通过删除校验、放宽权限或修改冻结设计让测试通过。

最低验收条件必须逐项给出“通过证据”。任何必选项失败时不得标记完成。

## 14. Git 差异检查

所有 Goal 完成自检时至少运行：

```bash
git status --short
git diff --name-status
git diff --check
git diff --stat
```

并按获准路径运行内容差异检查，例如：

```bash
git diff -- <明确获准文件路径>
```

若具体 Goal 明确涉及暂存区，还必须运行：

```bash
git diff --cached --check
git diff --cached --name-status
```

最终差异只能包含获准文件；`git diff --check` 无输出且退出码为 0 才能记录为通过。检查命令不授权暂存、提交或清理文件。

## 15. 最终回复要求

具体 Goal 应要求最终回复至少说明：

1. 完成的业务或技术闭环；
2. 修改、新增和删除的文件；
3. 数据表、字段、枚举、约束、依赖和配置变化；
4. 角色、权限、状态、阻断和审计变化；
5. 正常、异常、权限、非法状态、并发、约束和回滚结果；
6. 编译、测试、数据库、HTTP、浏览器和 Git 命令的真实结果；
7. 浏览器验收步骤或不适用原因；
8. 未完成项、风险、不能证明的内容和最终 Git 状态；
9. 是否执行 commit、push、合并、标签或外部写入。

没有发生变化的类别也应明确写“无”或“不适用，并说明原因”，不能省略后让读者猜测。

## 16. Goal状态与完成判定

| 状态 | 定义 |
| --- | --- |
| 未开始 | 尚未形成获准任务或没有实现证据 |
| 准备中 | 正在确认模板、依赖和决策，尚未开始实现 |
| 进行中 | 已按授权实现，但未达到全部交付物和验收条件 |
| 待验收 | 实现和自检完成，真实证据已提交，等待人工验收 |
| 已完成 | 全部书面条件通过且经人工确认 |
| 阻塞 | 存在未解决冲突、依赖、决策或外部条件，无法安全继续 |
| 取消 | 经人工决定终止，并记录原因和下游影响 |

状态判定规则：

- Codex 修改完成不等于 Goal 已完成；
- 文档存在不等于 Goal 已完成；
- 代码编译通过不等于业务验收通过；
- 自检全部通过通常只能进入“待验收”；
- 只有全部书面验收条件通过并经人工确认，才能标记为“已完成”；
- 失败、阻塞和取消必须保留真实原因，不能用状态名称掩盖未通过项。

## 17. 完整可复制模板

以下内容应复制到一个具体 Goal 的正式任务说明中再填写。尖括号是必须替换的明确占位符；不得保留模糊描述。

````markdown
# <GOAL编号>：<Goal名称>

> 本任务只对应一个正式 Goal。未列入允许范围的文件、数据库对象、依赖和配置不得修改。

### 填写规则

- 所有字段必填；不适用时填写：`不适用，并说明原因：<明确原因>`。
- 未关闭的技术事项写成决策点，不得擅自选定方案。
- 发现范围外问题只记录并报告，不自动处理。

### Goal 基本信息

| 字段 | 填写内容 |
| --- | --- |
| Goal编号 | `<DEMO_PLAN中的唯一Goal编号>` |
| Goal名称 | `<与DEMO_PLAN一致的Goal名称>` |
````

## 19. 维护规则

1. 本模板是任务边界模板，不得通过模板修改冻结产品、流程、状态、权限或数据库设计。
2. 模板字段、状态或证据规则需要调整时，应建立独立文档 Goal，并明确只允许修改的文件。
3. `DEMO_PLAN.md` 新增、拆分、取消或调整 Goal 后，应评估本模板是否仍能完整表达其授权和验收边界。
4. `CURRENT_STATE.md` 发生变化时，具体 Goal 以开始时现场证据为准，不把本模板中的版本信息当作实现完成证据。
5. `TECH_DEBT.md` 条目只有经当前仓库复核后才能进入具体 Goal。
6. 已启动 Goal 不因模板更新自动扩大范围；需要新增授权时必须重新人工确认。
7. 如模板与上位冻结文档或 `AGENTS.md` 冲突，停止使用冲突部分并等待人工修订。
8. 本文件已完成人工审查，当前作为 `v1.0 / 执行模板`；后续调整必须通过独立文档 Goal 并重新检查模板兼容性。
